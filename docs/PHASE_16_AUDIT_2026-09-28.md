## IMPLEMENTED

- explicit trust states;
- authenticated federation-session model;
- capability authorization model and the `authorize_federation_operation` composition boundary;

- idempotent synchronization decisions and divergence visibility;
- attributable federation conflicts;

- federation revocation, audit, diagnostics, and negative-governance domain coverage.

`DistributedMemoryGateway` also implements the intended **routing shape**:

- an unqualified profile uses `LiveMemoryGateway` locally;
- a qualified `<agent_id>:<profile>` source profile resolves an adopted discovered endpoint and reads from that endpoint's Mnemosyne API;
- a qualified profile does not fall back to a local profile when the named agent is unavailable.

The browser source-memory route delegates to this gateway and returns content transiently rather than storing it in `collective.db`.

## Blocking discrepancy

The formal federation domain is not wired into the live distributed source-memory read path:

1. `DistributedMemoryGateway` selects an endpoint only from discovery records whose legacy state is `ADOPTED`.
2. It constructs `AgentMemoryClient` and issues an ordinary HTTP GET to `/api/memories/{profile}/{memory_id}`.
3. That route invokes the same gateway and does not require a `FederationSession`, `FederationAuthorization`, or `FederationCapability`.
4. The only use of `authorize_federation_operation` is the domain `receive_remote_knowledge` path; the gateway and memory route do not invoke it.

Therefore the Phase 16 runtime route is discovery/adoption-gated, but it is not authenticated-session and capability-authorized federation exchange. It also returns source-memory content through a read-only API rather than a governed exchange envelope. This conflicts with the Phase 16 requirements that privileged federation communication authenticate the participant, enforce scoped capability authorization, and avoid raw private-memory exposure by default.

## Remaining closure work

Phase 16 cannot be accurately marked complete until all of the following are addressed and validated:

1. Bind distributed source-memory retrieval to an authenticated, active federation session and explicit least-privilege capability.
2. Define and enforce the policy for source-memory inspection across instances; it must not silently become a raw private-memory read API merely because an endpoint is discovered or adopted.
3. Preserve provenance, revocation, audit, and failure behavior through that runtime path, including stale/disallowed peer handling.
4. Add integration tests that exercise the actual gateway and HTTP transport with the enforcement boundary, not only mocked clients.
5. Perform and record an actual multi-machine Unraid/LAN browser validation if that deployment remains in scope.
6. Reconcile archival completion metadata, including a real completion commit/tag only after the preceding work passes.

## NOT PART OF PHASE 16

The following remain outside this audit's implementation scope:

- Jarvis, Laya, Open WebUI integration, a Jarvis dashboard, Markdown second-brain automation, daily maintenance automation, and voice;
- replacement of Hermes or redesign of Mnemosyne;
- broad production deployment changes beyond validating the existing source-routing behavior;
- automatic discovery adoption or automatic knowledge adoption.

## Conclusion

Phase 16's domain model and tests are substantially implemented and regression-clean, but the required governed runtime integration for distributed source-memory retrieval is absent. The project has a verified test baseline, not a clean Phase 16 closure boundary. No Phase 17+/Jarvis implementation should begin under a claim that this specific federation boundary is already enforced at runtime.
